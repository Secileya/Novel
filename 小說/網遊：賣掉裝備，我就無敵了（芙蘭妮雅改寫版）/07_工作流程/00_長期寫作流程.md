# 長期寫作流程

> 適用模式：Work 模式、一般 ChatGPT 對話或其他能讀取公開 GitHub 的對話。模式不改變正典、品質門檻或章節完整度；差別只在能否直接寫回倉庫。

## P0｜恢復真實當前狀態

- 從 `01_章節` 檔名與正文末實際確認最高正式章。
- 讀交接、當前狀態與事件佇列、數值稽核、章節索引。
- 確認改寫正文游標、原著消耗游標、遊戲時間與現實時間。

## P1｜定義連續事件窗

- 從當前原著游標展開到下一個硬時間錨及其完整第一層因果，不只看下一章。
- 長任務分接受、理解、準備、執行、回收；只消耗前置已成立的階段，不跳遠期結果。
- 活動窗內所有重要事件都進佇列，不允許空白或「以後再說」。

## P2｜原文證據

定位後讀連續前後文，抽取原著事實、人物知情、觸發條件、敘事功能、直接後果與下游依賴。命名人物另讀首次完整登場、當前場景與後續最顯人格的一場戲。

## P3｜Franiya 差分重算

> 本線現況 = 原著尚可成立的世界基線 + Franiya 與本線已固定條件 - 秦墨重生專屬前提 + 新因果自然導出的後果

每個節點標記保留、改寫、延後、世界側發生、條件成立才發生，或作廢並記原因。

## P4｜角色與聲線 Gate

- 所有當章有影響的命名人物都有最小人物卡。
- 次要角色、反對者、專業者、普通人與不同組織不共用同一句驚嘆。
- 對話先是人格、關係與當下目的，才是交代資訊。

## P5｜數值與戰鬥 Gate

- 有冷卻、攻速、僵直、位移、藥水、死亡、排名或勝負時，建立秒級時間軸。
- 用 `CALC_RECHECK / SILENT_CORRECTION / OUTCOME_REBUILD` 分流。
- 未知變量會改變勝負時，不偽造精準數字；讀更多原文或改用保守合法的場景。

## P6｜PREWRITE Gate

正文前寫明本章起點與終點、消耗的原著事件、不提前消耗的事件、每場景的局面變化、人物知情邊界、戰鬥驗算結果與章末停點。

## P7｜正文

- 使用繁體中文。
- 完整章一次交付，不分段試寫、不寫「待續」。
- 正常長章以 3～5 個完整場景、8,000～12,000 中文字為基本施工帶，但不為湊數字拉長。
- 可整合多個原著短章，但不摘要壓縮中間事件、人物反應與細節。
- 使用者說「開始寫」或「繼續」時，自動完成 Gate 後直接交付完整正文，不讓使用者等待內部施工。
- 普通對話同樣執行本段；不得以「需要 Work 模式」為理由只給提綱或拒絕寫章。

## P8｜POSTWRITE 與同步

- 回填正文游標與原著消耗游標。
- 更新事件佇列、狀態、未完成因果、知情、數值及章節索引。
- 反向稽核：是否偷用秦墨記憶？是否跳事件？是否有冷卻／攻速不可能？人物是否又變成同一種反應？
- commit 後才視為一輪正式同步完成。
- 若當前普通對話沒有倉庫寫入能力，先完整交付正文，再附「寫後同步包」：正文標題與檔名、正文游標、原著事件消耗游標、遊戲／現實時間、人物知情與數值變化、完成與新增因果、下一個不可跳過事件。這是待同步成果，不假稱已寫入或已提交。
