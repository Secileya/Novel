# 全球劇變末世（芙蘭妮雅線）｜正文只寫入 GitHub 與聊天狀態回報 Gate

> 建立日期：2026-10-03  
> 狀態：**WORKFLOW_FIXED_OVERRIDE / 正文交付方式最高優先級修正**

---

# 一、核心規則

使用者最新固定偏好：

> **正式正文不要再整章貼回聊天。**

後續正式章節、正文修訂、同章 Part 1 / Part 2 等內容，完成後直接寫入 GitHub `main` 對應正文檔。

聊天介面只回報施工狀態，不重貼正文全文。

---

# 二、聊天完成回報格式

正式正文完成後，聊天只需簡潔回報：

1. 完成到第幾正式章；
2. 本章實際消耗哪些 PREWRITE 節點；
3. POSTWRITE Gate：PASS／有何修正；
4. 主要新增或回收了哪些因果；
5. 修改／新增哪些檔案；
6. GitHub commit SHA；
7. 下一步施工範圍。

除非使用者明確要求查看正文、節錄、指定場景或全文，否則不要把正文複製到聊天。

---

# 三、與 writing block 舊規則的關係

舊規則「正式聊天交付章節時，章名與全文放同一 writing block」只在**使用者明確要求於聊天顯示正文**時適用。

正常 GitHub 長篇施工流程中：
- 正文直接進 repo；
- 聊天不建立正文 writing block；
- 只回報狀態。

本檔覆蓋任何要求每次完成正文都必須在聊天全文重貼的舊流程描述。

---

# 四、零上下文 Gate

新模型若準備正式續寫本線，完成 GitHub 寫入後不得因習慣再次輸出整章。

固定收尾形態：

> **正式正文：**第 X 章已完成。  
> **消耗節點：**PREWRITE X～Y。  
> **POSTWRITE：**PASS。  
> **主要推進：**……  
> **GitHub：**commit `……`。  
> **下一步：**……

篇幅依實際內容保持簡潔。

---

# 五、例外

只有以下情況可在聊天顯示正文：
- 使用者明確說「貼出來」「給我看全文」；
- 使用者指定要看某一段／某場戲；
- 使用者要求比較修訂前後文字；
- 無法成功寫入 GitHub，且需要讓使用者先取得正文內容。

即使屬例外，也依既有完整段落與 writing block 規則處理。
