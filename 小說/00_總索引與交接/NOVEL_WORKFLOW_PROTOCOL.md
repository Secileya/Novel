# NOVEL WORKFLOW PROTOCOL

> 用途：讓任何新對話／新模型在不依賴舊聊天上下文的情況下，從 GitHub 恢復小說工作狀態並正確續寫。

## A. 長期記憶原則

GitHub 是 canonical memory。模型只需要記得「去哪裡讀」，不需要永久記住所有章節。

權威順序固定為：

1. 最新有效正文
2. 後來明確修正、撤回、作廢聲明
3. 穩定世界觀／角色／能力設定
4. 連續性與索引工作檔
5. 聊天摘要、Memory、模型印象

工作檔不是第二份正文。若工作檔與正文衝突，以正文為準並修正工作檔。

## B. 新對話／久未接手時的固定讀取程序

1. 讀 `PROJECT_HANDOFF_MASTER_v0.1.md`
2. 確認使用者指定的作品、正史／分支／世界線
3. 讀該線 `00_專案交接.md` 或對等交接檔
4. 讀「當前狀態快照」
5. 讀「未完成因果與伏筆」
6. 讀「角色知識矩陣」
7. 讀「修正與禁用設定」
8. 讀「交易與資產台帳」（該線若有）
9. 讀「章節續寫索引」
10. 讀最近 2–5 章正文
11. 本次若牽涉早期事件／舊承諾／能力細節，再回查對應原文

只有完成必要讀取後才正式續寫。

## C. 續寫前必做自檢

至少確認：
- 現在時間、地點與視角
- 當前傷勢、裝備、重要物件
- 每名角色「知道／不知道／只是推測」什麼
- 尚未完成的委託、交易、契約、調查與責任鏈
- 本章會碰到哪些穩定世界規則／能力限制
- 哪些舊設定已作廢
- 哪些兄弟分支事件禁止混入
- 下一章自然入口是否來自已存在的因果，而不是模型臨時造主線

## D. 寫作原則

- 續寫不是重寫；從最新有效斷點自然接續。
- 正式正文的敘事層不得用「第X章」「上一章」「本章」「前一章」等作者／章節編號來回指已發生事件；除章名、目錄、檔案索引或明確後設敘事外，角色與旁白都應改用世界內可成立的時間、地點、事件、任務或記憶稱呼，例如「灰橋那一夜」「押送事件」「離開補給站前」。
- 不因作者知道而讓角色知道。
- 不自行補完尚未確立的設定。
- 不為了展示某個系統而強行生成 E.G.O、扭曲、女聲、金枝或重大揭露。
- 世界必須能在主線之外自行運作；普通工作、物流、契約、犯罪、事故與生活可獨立成立。
- 重大角色／力量／社會重量應靠場景、反應與因果呈現，不只靠旁白宣告。
- 未完成伏筆可長期存在，不必每章回收。
- 兄弟非正史分支只能作參考；事件不得自動互通。

## E. 正文完成後的同步程序

每完成一章或一批正式正文，依序：

1. 保存完整正文
2. 更新當前狀態快照
3. 更新未完成因果與伏筆
4. 更新角色知識矩陣
5. 若有永久角色／世界／能力變化，更新穩定設定
6. 若舊說法失效，更新修正與禁用設定
7. 若有金錢、館藏、武器、特殊物件、合同、證物、所有權變動，更新交易與資產台帳
8. 更新章節續寫索引
9. 自檢本章是否造成分支污染、知情越界、能力越界
10. commit

## F. Canonical checkpoint

只有「正文＋相關工作記憶均同步完成」的 commit 才能標記為 canonical checkpoint。

該線 `00_專案交接.md` 應記錄：
- 正典 checkpoint SHA
- 最新正文
- 狀態同步至哪一章
- 下一自然入口
- 尚未同步項目

為避免 commit 自我引用，允許下一個只修改交接指標的 commit 記錄上一個完整同步 commit SHA。這種「指標 commit」不改變故事正典。

## G. 角色知識矩陣規則

至少區分：
- 親眼／親身確認
- 由可靠來源得知
- 公開資訊
- 推測
- 不知道
- 作者層資訊，角色不可用

「A 知道」不代表「A 的同組織所有人都知道」；「讀者知道」不代表角色知道。

## H. 工作檔維護原則

- 當前狀態只保存「現在」，不要寫成第二份長篇歷史。
- 未完成因果只記仍有後續可能的事項，並可標記「近期」「長期」「背景」。
- 修正禁用檔只記容易復活的舊稿、明確禁區與常見誤寫。
- 章節索引只提供定位與結果，不取代正文。
- 台帳記錄重要交易、合同、物件、館藏、證物與所有權，不把所有日用品塞進去。


## I. 外部原作全文／考據來源

當小說專案屬於改編、同人、重寫或明確依賴既有作品，且使用者已提供完整原作文本時，原作考據固定採以下優先順序：

1. 目前專案／世界線已成立的 GitHub 正典。
2. 使用者提供的完整原作文本。
3. 官方／第一方網站或可核驗的正式資料。
4. 可靠的網路轉載、索引與搜尋結果。
5. 模型記憶。

若續寫即將接觸尚未改編的原作事件、人物、商品、能力、任務或時間順序，必須先：

- 在完整原作文本中定位對應章節或關鍵詞。
- 閱讀足夠的連續上下文；不得只憑搜尋片段或單句摘要判定事件。
- 核對事件順序、在場人物、已知資訊、物件／交易、能力與結果。
- 再與目前世界線 GitHub 正典比較，決定哪些原作骨架仍可使用、哪些已被改編分歧取代。

已被本線正文改寫的內容，以本線 GitHub 正典為準；完整原作文本主要約束「尚未被本線正式改編」的部分。

若完整文本在新的工作階段不可存取，不得以模型記憶補寫原作。應改用可核驗網站／正式來源重新考據，或明確標記來源缺失。

原作文本只作考據與改編依據，不應在輸出中大量逐字重製受版權保護的正文。


## J. 每章至少一個核心看點

每一章至少應具有一個清楚可辨認的「章節核心／看點／功能重心」，使讀者在章末能感覺本章有實際價值，而不是只把人物從 A 點搬到 B 點。

這個核心不等於每章都必須出現重大事件、戰鬥、覺醒、死亡、巨大揭露或主線突破。可成立的章節核心包括但不限於：

- 必要且有戲劇性的資訊統整、報告、盤點或界線確認。
- 人物關係發生細微但真實的變化。
- 某角色作出新的選擇、承認、拒絕、習慣或日常行為。
- 前置鋪墊、任務準備、情報取得、設備／制度／社會運作展示。
- 前一事件的後果處理、善後、責任劃分或社會反應。
- 一場普通委託、物流事故、地方衝突、生活事件或工作問題。
- 一個值得記住的情緒轉折、人物瞬間、觀點或世界細節。
- 伏筆被推進一小步，但不必回收。
- 讓世界證明即使主線不前進，人物與都市仍在自行生活與運作。

資訊統整章可以成立，只要統整本身具有必要性、人物反應與新的理解，不是把既有內容改寫成摘要。例：合聲線第六章開頭透過事故報告確認「未知可以留白」、「不能把個人責任提前合併成合聲整體責任」，就是有效章節看點。

反過來，不要為了滿足「每章有看點」而硬塞重大事件。若一章主要功能是前置、過渡、日常或後果處理，也可以成立；但至少應有一個能讓本章與前後章區分開來的具體價值，例如新的理解、人物推進、因果變化、重要細節或完整小場景。

寫完每章後自檢：
- 本章最值得記住的是什麼？
- 若刪掉整章，會失去哪個人物、因果、資訊、情緒或世界運作價值？
- 若答案只是「人物走到下一個地點」，應補足本章真正的核心，而不是硬加大型事件。


## K. 人物聲音、原作事件穿插與臨界後效應

### K1. 角色性格不是口癖表

- 對話必須讓每個角色保有可辨認的個性、節奏、關係感與當下狀態，但不得把性格簡化成固定標籤、固定功能或機械口癖。
- 「會爆粗口」不等於每句都爆粗；「文質彬彬」不等於任何極端情境都維持完整禮貌；「冷靜」「活潑」「毒舌」「寡言」「自嘲」「哲思」「愛開玩笑」等同樣不能每句都硬展示。
- 性格應被理解為穩定傾向，而不是固定輸出模板。同一人面對朋友、陌生人、上司、家人、敵人，或處於工作、疲勞、受傷、羞恥、憤怒、恐懼、危險、失敗、喪親、公開場合與私人場合時，都可能自然改變措辭、語速、句長、禮貌程度與是否願意說話。
- 喜歡開玩笑的人在嚴肅場合也可能沉默、收斂、只低聲說一句，甚至完全笑不出來；同伴死亡、重傷、重大失敗或真正恐懼時，不得為了維持「搞笑役」功能硬安排大聲逗笑全場的台詞。若角色仍會用玩笑應對壓力，也應符合當時關係與情緒重量，例如乾澀、自嘲、私下、短促，而不是機械緩解氣氛。
- 平時有教養、文質彬彬的人在劇痛、暴怒、失控、極端緊迫或面對特定熟人時，也可能省略禮節、說重話、爆粗或只剩最直接的短句；這不自動等於人物崩壞，關鍵在是否由當下情境與既有人格自然推出。
- 沉默、停頓、答非所問、換話題、說一半停下、重複、口誤、語氣失衡、刻意正常、避開視線等，都可以是人物正在真實生活中的說話反應；不要讓每句台詞都像作者為了展示性格精心準備的「代表句」。
- 同一角色也不必每次都對同類事件做出相同反應。經驗、關係進展、傷勢、心境、近期遭遇與成長都可以改變當下表現，但應保留可追溯的人格連續性。
- 罪人、嚮導、司機、合聲成員、敵人、合作方、學生、師長、店主與普通路人都遵守同一原則：先寫成正在當下生活、思考與說話的人，再保留其穩定人格傾向。
- 不要讓某角色只剩「負責爆粗」「負責哲學」「負責吐槽」「負責冷臉」「負責解說」「負責活躍氣氛」「負責理性收尾」等單一功能。

### K2. 原作主線與分支內容可以互相穿插

- 改編／同人線不必把自創主線與原作主線分成互不干擾的兩條軌道。
- 原作正式事件可以在本線繼續發生、被提前、延後、插入、打斷或因已成立的分支因果而產生偏移；前提是先核對原作來源與本線正典。
- 某個原作任務可以在途中自然碰上分支人物、女聲、E.G.O、扭曲、臨界或其他已建立因素；分支事件也可以被原作任務、公司命令、地方事故或角色私人事件打斷。
- 不要因章節標題／主題而讓世界排隊：角色的人生、任務與外部事件可以同時進行並互相干擾。

### K3. 臨界必須由人物與事件自然推到

- 隊友、主角群、敵人、合作方或其他重要人物，只要其人生與當前事件真正把他推至相應心理／自我臨界，都可以自然進入核心事件；身分不是限制。
- 不得因「輪到某人」「這章需要高潮」「很久沒寫女聲」而硬觸發臨界。
- 既有角色若曾被規劃為未來可能有第二次／延伸式臨界，也只代表可能性；具體發生時間仍由當下因果決定。

### K4. 臨界回歸後必須有餘震，但不強制開會

- 人物從核心／臨界返回後，事件不能像什麼都沒發生一樣立刻平靜帶過；其身體、情緒、注意力、關係或後續行為應留下符合事件重量的餘震。
- 餘震不等於全員立刻圍著當事人長篇討論。若戰鬥、撤離、救援或其他危險仍持續，優先處理安全、補位、確認能否行動、保護當事人或完成眼前任務。
- 安全後的反應可分散在之後數分鐘、數小時甚至數章：沉默、遞水、避免追問、遲來的一句話、失眠、動作變化、主動找特定人物、刻意維持日常、情緒失控、研究需求、警戒或私人關係改變都可以。
- 反應強度與方式依人物個性、彼此關係、是否親身見過女聲、對女聲的感情、是否需要確保安全、是否屬合聲等因素決定。
- 合聲成員或對女聲有深厚正面感情者，得知另一人真正見過她時，可以有更明顯的興奮、安心、親近、好奇、保護欲、沉默或情緒重量；仍不得統一成同一反應，也不得自動跨越對方私人核心界線。
- 沒見過女聲的人也可能好奇、懷疑、擔心、研究、害怕、不知如何安慰、故意不問或把注意力放在作戰安全；這些都應依人物成立。
- 敵人不必尊重臨界。若仍在交戰，對方完全可能利用當事人剛回神的空隙。


## L. 設定外部化的詳細度原則

- GitHub 設定／連續性文件的首要用途是讓後續模型能在換對話後恢復精準執行，不以「檔案越短越好」為目標。
- 對真正會影響執行的內容，優先保存完整條件、例外、資訊順序、角色知識邊界、正反例、後修與禁用版本；若省略後會迫使後續模型自行猜測，寧可保留較長的詳細版本。
- 對話整理進 GitHub 前必須讀到該串後續修正：早期方案若後來被拒絕、覆蓋、降為候選或改名，不得因先出現就當成現行設定。
- 可以同時保存「穩定規則」與「詳細補錄」：穩定設定負責快速定位，詳細補錄負責保留推理邊界與例子；兩者衝突時仍依最新有效正文與後修優先序處理。
- 這項原則只影響設定記錄的完整度，**不要求正文變成條列、說明書或設定集語氣**；小說正文仍依各專案既有敘事風格自然呈現。
