# NOVEL WORKFLOW PROTOCOL

> 用途：讓任何新對話／新模型在不依賴舊聊天上下文的情況下，從 GitHub 恢復小說工作狀態並正確續寫。

## A0. 零知識啟動閘門（ZERO_CONTEXT_BOOTSTRAP_GATE）

任何新對話／新模型／長時間未接手的工作階段，一律視為**沒有任何可靠先備知識**。本 Gate 的目的，是讓完全不知道 repo、檔名、世界線、正文進度與設定歷史的模型，也能靠文件恢復到可工作的完整狀態。

### 觸發

以下任一成立即觸發：
- 新開普通對話；
- 模型／模式切換；
- 上下文被截斷或大量壓縮；
- 使用者要求「接手」「沿用之前設定」「繼續之前小說」；
- 模型無法從當前上下文明確證明自己已讀過本工作階段需要的來源。

### 固定順序

1. 讀 `PROJECT_HANDOFF_MASTER_v0.1.md`。
2. 讀本 `NOVEL_WORKFLOW_PROTOCOL.md`。
3. 確認使用者指定的作品／正史／分支／世界線；若使用者已明確指定，不再反問。
4. 讀該線 `00_專案交接.md`。
5. 按交接檔的精確路徑逐項讀必要來源文件。
6. 讀最近 2–5 章正式正文。
7. 建立本輪「狀態重建表」：
   - 最新正文與停點
   - 當前人物／地點／傷勢／物件
   - 知識邊界
   - 硬設定
   - 候選／待決
   - 最近後修／禁用
   - 本輪任務涉及主題
8. 若使用者指向舊對話／漏存／以前談過，先完成 CONVERSATION_RECOVERY_GATE。
9. 再進 TOPIC_SWEEP_GATE。
10. 涉及原作差分時先進 CANON_EVIDENCE_AUDIT，再進 CANON_DIVERGENCE_GATE。
11. 需要正式續寫時才進 PREWRITE_GATE。

### 路徑未知時

完全零知識模型如果不知道文件在哪裡：
- 先靠 Master 中的入口；
- 若入口檔提到的路徑失效，必須在 repo 搜檔名／關鍵詞；
- 找到後回修交接路徑；
- 不得因自己猜得到大概位置就略過。

### 長檔與截斷

- 一次 fetch 長檔被截斷，不算讀完。
- 對本輪主題必須用關鍵詞／段落範圍重新抓取。
- 「檔名已讀」不能作為 Gate PASS 證據。

### PASS 條件

只有當模型能**從當前工作階段已讀文件**重建世界線狀態，而不是靠舊記憶，才能判定：

**ZERO_CONTEXT_BOOTSTRAP_GATE = PASS**

此 Gate PASS 後，才允許重大設定判斷、規劃整合或正式續寫。

## A0.5 流程不得依賴隱性熟悉度（NO_TACIT_CONTEXT_RULE）

這條規則適用於**所有流程**，不只新對話交接。

任何 Gate、核定表、設定同步、正史差分、正文同步、名稱遷移或舊對話恢復，都必須設計成：

> 一個完全不知道前情、沒有模型記憶、沒有舊聊天、甚至不知道檔案放哪裡的新模型，只靠 Master／Workflow／分支交接與 GitHub 搜尋，也能正確執行。

因此每個流程都必須具備：

1. **Trigger**：什麼情況會觸發。
2. **Inputs**：需要讀哪些精確文件／來源。
3. **Actions**：按什麼順序做。
4. **Outputs**：要產生／更新哪些文件或內部核對結果。
5. **PASS／FAIL**：什麼情況才算完成。
6. **Failure handling**：路徑失效、資料截斷、來源衝突、工具失敗時怎麼辦。
7. **Persistence**：完成後如何讓下一個新對話知道已做過什麼。

禁止：
- 「這個模型知道設定在哪，所以不用寫路徑」；
- 「上一輪已經懂，所以這輪可跳過來源」；
- 「流程文件只寫概念，實際順序靠熟悉專案的人自行補」；
- 「只有當前聊天知道的決策沒有落盤」；
- 「用模型記憶補流程缺口」。

### 能力等價目標

流程完成的標準不是「新模型看過檔案」，而是新模型應能達到**能力等價**：
- 能辨別正典／候選／作廢；
- 能定位最新正文與停點；
- 能維持角色知識邊界；
- 能找到相關舊設定而不是重新發明；
- 能做 Project Moon 正史差分推導；
- 能知道哪些地方不能自行決定；
- 能在完成工作後把新差分同步給下一個模型。

若某流程只有熟悉專案的模型才能正確執行，該流程本身就視為**不完整**，應立即補文件，而不是把熟悉度當成安全保障。

## A0.6 上位世界繼承與分支隔離（PARENT_WORLD_INHERITANCE）

分支隔離只禁止**兄弟分支專屬事件結果**互相污染，不代表分支脫離上位共同世界。

固定優先層級：
1. 上位世界總設定／共同歷史；
2. 目前世界線共同規則；
3. 目前分支覆蓋；
4. 目前分支正式正文。

因此，上位總檔中的世界制度、都市生態、組織、人物／組織基線、任務、長期因果、地區、產業、危險分類等，原則上全部繼承；只有目前分支明確衝突／覆蓋才例外。

對都市世界觀尤其要注意：
- 清道夫、協會、翼、五指、辛迪加、事務所、工坊、巢／後巷、異想體、L 公司遺跡、危險分類等，不會因鏡頭暫時離開就消失；
- 兄弟分支的具體「已發生事件、角色知情、關係進度、物件狀態」仍不可繼承；
- 正式續寫不必硬插所有都市生態，但必須先確認當地／當時是否有自然應出現的背景因素。

### 正式正文聊天版／GitHub 版一致性核對（FORMAL_PROSE_RECONCILIATION）

當使用者明確指出「對話裡有正式章節」「GitHub 可能另有修改版」「這兩個版本哪個才是正式」時，或流程本身偵測到同章存在聊天正式版／GitHub 版不一致風險時：

1. **不得只相信 GitHub 檔名或交接摘要。**
2. 先透過 CONVERSATION_RECOVERY 找回：
   - 使用者明確接受／指定為正式的聊天版本；
   - 該版本前後是否還有後來修訂、撤回、重寫、另存正式版的訊息。
3. 再抓取 GitHub 當前同章完整正文。
4. 優先做**全文逐段／逐字 diff**；若舊對話檢索只能取回片段，最多只能說「已核對可取回片段一致」，不得宣稱全文完全相同。
5. 權威判斷：
   - 較晚的使用者明確修正／正式重寫 > 較早聊天正式版；
   - 若聊天正式版是較晚且 GitHub 沒同步完整，應修 GitHub；
   - 若 GitHub 是後來依使用者明確修正完成的正式版，聊天舊版視為歷史版本。
6. 第十二章這類曾同時存在「未核定草稿＋後來正式重寫版」的情況，必須先排除草稿，**只拿最後被接受的正式聊天版和 GitHub 比**。
7. 比對完成後把結果寫入分支交接／必要的修正檔，避免下一個對話再次混淆。

這個流程只在存在「聊天正文與 GitHub 正文可能不一致」的實際風險時觸發，不要求每次續寫都重查所有歷史聊天正文。

## A. 長期記憶原則

GitHub 是 canonical memory。模型只需要記得「去哪裡讀」，不需要永久記住所有章節。

權威順序固定為：

1. 最新有效正文
2. 後來明確修正、撤回、作廢聲明
3. 穩定世界觀／角色／能力設定
4. 連續性與索引工作檔
5. 聊天摘要、Memory、模型印象

工作檔不是第二份正文。若工作檔與正文衝突，以正文為準並修正工作檔。

## B-1. 對話恢復與 GitHub 完整性稽核（CONVERSATION_RECOVERY_GATE）

GitHub 是長期正典記憶，但**不能先驗假設 GitHub 已經完整保存所有曾定案的舊對話內容**。當使用者明確指向舊討論、說「之前談過」「那個對話」「你應該有叫他存 GitHub」「沿用舊對話」「看看有沒有漏存」，或指出現有流程／GitHub 漏掉先前討論時，必須先跑本閘門，再進 PREWRITE_GATE。

觸發時必做：

1. 盡可能檢索／恢復使用者指定的舊對話與相關上下文；不能只取第一個搜尋片段。
2. 必須往後讀到可能的修正、否定、改名、降級為候選或作廢版本，避免「先出現的版本」錯當現行版本。
3. 將恢復內容分類為：
   - 已定案／硬設定
   - 後修覆蓋
   - 候選／可調參考
   - 作廢／拒絕
   - 僅為討論、尚未定案
4. 與 GitHub 逐項比對：
   - 舊對話已定案但 GitHub 漏存 → 補進 GitHub；
   - GitHub 留有但舊對話後來否定／修正 → 更新或標記失效；
   - 正式正文與舊討論衝突 → **不得靜默改正文**；先列出衝突，由正文權威規則處理，必要時請使用者決定是否修正文。
5. 對會影響續寫的遺漏完成同步後，才能判定：
   **CONVERSATION_RECOVERY_GATE = PASS**
6. 若舊對話當前不可完整取得：
   - 明確標記恢復範圍與缺口；
   - 不得假稱「已完整恢復」；
   - 對缺口涉及的設定不得自行補完。

聊天／Memory 在一般情況下仍只作導航；但當任務本身就是「恢復先前已討論內容、檢查 GitHub 是否漏存」時，它們是**GitHub 完整性稽核的來源證據**。完成稽核並同步後，才由 GitHub 繼續承擔長期正典記憶。

## B0.5. 主題式全庫回查（TOPIC_SWEEP_GATE）

固定讀檔只是最低底線，**不能把「已 fetch 一份很長的檔案」視為真的讀到其中所有相關細節**。大型設定檔／規劃檔可能因輸出截斷、上下文壓縮或關鍵段落位於很後面而被漏掉。因此，任何正式續寫或重大設定判斷，在 PREWRITE_GATE 前都必須再做一次「本章／本問題主題式全庫回查」。

### 觸發範圍

至少從下列來源建立本輪主題清單：

- 使用者本輪直接點名的人物、事件、能力、館藏、組織、地點、機制；
- 最新正文停點中即將繼續使用的具名人物／物件／伏筆；
- 本章預計碰到的候選規劃與原作事件；
- 已知容易有後修／禁用／舊版本衝突的主題。

### 每個主題必做

1. 在目標世界線 GitHub 中做關鍵詞／語義回查，不得只依賴交接摘要。
2. 同時搜尋：
   - 中文正式名；
   - 外文／英文名；
   - 舊譯名、曾用名、別名、能力名、事件名；
   - 必要時連同「後修／禁用／作廢／候選／正式／正文」等狀態詞一起查。
3. 至少核對命中於：
   - 穩定設定；
   - 詳細補錄；
   - 修正與禁用；
   - 後續候選／規劃；
   - 相關正式正文。
4. 對每個主題建立內部 **TOPIC_COVERAGE_MAP**：
   - 主題
   - 搜尋詞／別名
   - 命中文件
   - 狀態：硬設定／後修／候選／作廢／正文既成
   - 是否存在衝突
5. 若長檔 fetch 出現截斷，**必須改用定向搜尋／局部讀取補足**；不能因「已經抓過整份檔」就當成讀完。
6. 同一主題若存在不同年代版本，必須讀到較晚的修正；不能採第一個搜到的版本。
7. 若發現高影響衝突：
   - 本章會碰到該衝突 → PREWRITE_GATE 不得 PASS，先請使用者決定或改寫避開；
   - 本章不碰該衝突 → 可以繼續，但必須把衝突保留在工作檔，不能忘記。

### 名稱後修必須做全庫正規化（CANONICAL_NAME_MIGRATION）

當人物名、譯名、組織名、能力名、事件名、館藏名或術語被正式更正／改名時，不能只新增「舊名 → 新名」備註。

必做：

1. **立即以新正式名回寫所有現行有效文件。**
   - 正式正文中的純誤譯／誤名；
   - 穩定設定；
   - 當前狀態；
   - 未完成因果；
   - 角色知識矩陣；
   - 後續候選規劃；
   - 交接檔；
   - 其他仍會被未來續寫直接讀取的工作檔。
2. 舊錯名原則上只保留在：
   - Git 歷史；
   - `主題與別名索引`中的「舊稱／誤譯 → 現行正式名」映射；
   - 必要的修正／禁用紀錄中，以最小篇幅作防復活提示。
3. **現行設定內容本身不得繼續以舊名作主詞。**未來模型只知道正確名，也應能直接搜到所有仍有效資料。
4. 改名後必須用**新正式名**做一次全庫搜尋，確認主要有效資料都能被新名命中。
5. 再用舊名做一次清掃搜尋；若舊名仍出現在現行有效內容中：
   - 純誤譯／舊稱 → 改成新名；
   - 歷史引用／禁用說明 → 可留，但同段必須明確標示新正式名；
   - 若無保留必要 → 移除。
6. 主題式回查時，**第一搜尋詞永遠是現行正式名**；別名索引只用來擴展第二輪搜尋，不要求模型自己猜出曾經的錯名。

目的：避免「資料其實存在，但只寫在舊名字底下，導致只知道正確名稱的新對話搜不到」。

### 主題清單必須動態增長

- TOPIC_SWEEP 的主題與搜尋詞**不是固定清單**。
- 每次後續討論只要新增了重要人物、別名、舊譯名、能力名、事件名、組織名、館藏名、術語、代號、伏筆或新的後修關係，就必須把它加入未來可檢索範圍。
- 新增項目若會長期反覆使用，應同步到該世界線的「主題／別名索引」或等價文件；不能只存在單次對話中。
- 某主題一旦出現新的別名／譯名／作者層稱呼，後續搜尋時應把新舊名稱一起查，避免因改名後只搜新名而漏掉舊討論。
- 某主題後來被拆分成兩個概念時，也要保留舊詞作回查入口，並在索引中標註「舊稱／已拆分／勿混用」。
- 每次 POSTWRITE 或設定同步後，若本輪新增了會影響未來檢索的新名稱／主題，應一併更新索引。

### PASS 條件

只有當本輪所有「會直接影響正文／設定回答」的主題都完成回查，且沒有未處理的高影響衝突時，才能判定：

**TOPIC_SWEEP_GATE = PASS**

此閘門的目的，是避免「GitHub 明明早已保存，但模型因只讀摘要／長檔被截斷而表現得像第一次知道」。

### 呼叫語句不得凍結流程版本

使用者若以一句話要求「依所有流程接手並續寫」，該句話只是**觸發最新 Workflow**，不是把當時的 Gate 名稱／順序永久寫死。

因此：
- 若未來新增 Gate，必須自動納入；
- 若 Gate 改名／合併／拆分，依最新文件；
- 若讀取順序調整，依最新文件；
- 若新增同步檔案／索引／核定表，也必須執行；
- 舊聊天中的固定 Gate 清單不得覆蓋 GitHub 最新有效流程。

## Gate 總順序

一般重大設定／規劃：
`ZERO_CONTEXT_BOOTSTRAP_GATE →（必要時 CONVERSATION_RECOVERY_GATE）→ TOPIC_SWEEP_GATE →（涉及原作時 CANON_EVIDENCE_AUDIT → CANON_DIVERGENCE_GATE）→ 設定判斷 → SETTINGS_HANDOFF_SYNC`

正式續寫：
`ZERO_CONTEXT_BOOTSTRAP_GATE →（必要時 CONVERSATION_RECOVERY_GATE）→ TOPIC_SWEEP_GATE → CANON_EVIDENCE_AUDIT（若涉及原作）→ CANON_DIVERGENCE_GATE（若涉及原作）→ PREWRITE_GATE → 正文 → POSTWRITE_GATE → SETTINGS_HANDOFF_SYNC`

任何 Gate 失敗都不得用模型熟悉度跳過。

## B0. 正式續寫硬閘門（PREWRITE_GATE）

只要使用者要求「繼續」「下一章」「續一章」「接著寫」「寫第X章」或任何等價的正式小說續寫，**第一個工作步驟不是起草正文，而是完成該世界線的續寫前核定流程。使用者不需要再次提醒。**

硬規則：

- **未得到 PREWRITE_GATE = PASS 前，禁止輸出正式正文。**
- 不得以聊天記憶、Memory、摘要、最近兩章、模型印象或「之前讀過」替代必要讀取。
- 若該線有專屬「續寫前核定表」，必須完整執行。
- 若涉及尚未被本線改編完成的原作事件，必須另完成原作／外部來源核對；來源缺失時不得用模型記憶補寫。
- 若先前在未核定情況下生成章節，該內容只能算未核定草稿，不得自動成為正文或下一章起點。

正式正文完成後仍需完成同步程序並得到 POSTWRITE_GATE = PASS，才可進入 canonical checkpoint。

## B. 新對話／久未接手時的固定讀取程序

本節不再維護另一套簡化清單，避免與 A0 的零知識流程漂移。

固定做法：
1. 完整執行 **ZERO_CONTEXT_BOOTSTRAP_GATE**；
2. 依目標世界線 `00_專案交接.md` 的精確讀取順序載入來源；
3. 建立 TOPIC_SWEEP；
4. 涉及原作時先 **CANON_EVIDENCE_AUDIT**，再 **CANON_DIVERGENCE_GATE**；
5. 只有正式續寫才進 **PREWRITE_GATE**。

若本節、Master、分支交接三者的讀取順序不一致，以：
**Master → Workflow → 分支交接 → 分支來源檔 → 最近正文 → TOPIC_SWEEP → Evidence/Divergence → PREWRITE**
為唯一有效順序，並應回修漂移文件。

## C. 續寫前必做自檢

至少確認：
- 現在時間、地點與視角
- 當前傷勢、裝備、重要物件
- 每名角色「知道／不知道／只是推測」什麼
- 尚未完成的委託、交易、契約、調查與責任鏈
- 本章會碰到哪些穩定世界規則／能力限制
- 哪些舊設定已作廢
- 哪些兄弟分支事件禁止混入
- 下一章自然入口是否來自已存在的因果，而不是模型臨時造主線

## D. 寫作原則

- 續寫不是重寫；從最新有效斷點自然接續。
- 正式正文的敘事層不得用「第X章」「上一章」「本章」「前一章」等作者／章節編號來回指已發生事件；除章名、目錄、檔案索引或明確後設敘事外，角色與旁白都應改用世界內可成立的時間、地點、事件、任務或記憶稱呼，例如「灰橋那一夜」「押送事件」「離開補給站前」。
- 不因作者知道而讓角色知道。
- 不自行補完尚未確立的設定。
- 不為了展示某個系統而強行生成 E.G.O、扭曲、女聲、金枝或重大揭露。
- 世界必須能在主線之外自行運作；普通工作、物流、契約、犯罪、事故與生活可獨立成立。
- 重大角色／力量／社會重量應靠場景、反應與因果呈現，不只靠旁白宣告。
- 未完成伏筆可長期存在，不必每章回收。
- 兄弟非正史分支只能作參考；事件不得自動互通。

## E. 正文完成後的同步程序

每完成一章或一批正式正文，依序：

1. 保存完整正文
2. 更新當前狀態快照
3. 更新未完成因果與伏筆
4. 更新角色知識矩陣
5. 若有永久角色／世界／能力變化，更新穩定設定
6. 若舊說法失效，更新修正與禁用設定
7. 若有金錢、館藏、武器、特殊物件、合同、證物、所有權變動，更新交易與資產台帳
8. 更新章節續寫索引
9. 自檢本章是否造成分支污染、知情越界、能力越界
10. commit

## F. Canonical checkpoint

只有「正文＋相關工作記憶均同步完成」的 commit 才能標記為 canonical checkpoint。

該線 `00_專案交接.md` 應記錄：
- 正典 checkpoint SHA
- 最新正文
- 狀態同步至哪一章
- 下一自然入口
- 尚未同步項目

為避免 commit 自我引用，允許下一個只修改交接指標的 commit 記錄上一個完整同步 commit SHA。這種「指標 commit」不改變故事正典。

## G. 角色知識矩陣規則

至少區分：
- 親眼／親身確認
- 由可靠來源得知
- 公開資訊
- 推測
- 不知道
- 作者層資訊，角色不可用

「A 知道」不代表「A 的同組織所有人都知道」；「讀者知道」不代表角色知道。

## H. 工作檔維護原則

- 當前狀態只保存「現在」，不要寫成第二份長篇歷史。
- 未完成因果只記仍有後續可能的事項，並可標記「近期」「長期」「背景」。
- 修正禁用檔只記容易復活的舊稿、明確禁區與常見誤寫。
- 章節索引只提供定位與結果，不取代正文。
- 台帳記錄重要交易、合同、物件、館藏、證物與所有權，不把所有日用品塞進去。


## I. 外部原作全文／考據來源

當小說專案屬於改編、同人、重寫或明確依賴既有作品，且使用者已提供完整原作文本時，原作考據固定採以下優先順序：

1. 目前專案／世界線已成立的 GitHub 正典。
2. 使用者提供的完整原作文本。
3. 官方／第一方網站或可核驗的正式資料。
4. 可靠的網路轉載、索引與搜尋結果。
5. 模型記憶。

若續寫即將接觸尚未改編的原作事件、人物、商品、能力、任務或時間順序，必須先：

- 在完整原作文本中定位對應章節或關鍵詞。
- 閱讀足夠的連續上下文；不得只憑搜尋片段或單句摘要判定事件。
- 核對事件順序、在場人物、已知資訊、物件／交易、能力與結果。
- 再與目前世界線 GitHub 正典比較，決定哪些原作骨架仍可使用、哪些已被改編分歧取代。

已被本線正文改寫的內容，以本線 GitHub 正典為準；完整原作文本主要約束「尚未被本線正式改編」的部分。

若完整文本在新的工作階段不可存取，不得以模型記憶補寫原作。應改用可核驗網站／正式來源重新考據，或明確標記來源缺失。

原作文本只作考據與改編依據，不應在輸出中大量逐字重製受版權保護的正文。


### 舊流程缺陷修正：不能只核「有沒有查到」

先前流程雖要求原作核對與差分推導，但缺少「**考據是否真的覆蓋足夠來源**」這一層，因此仍可能出現：
- 查到一個總頁就停止；
- 知道某角色的著名狀態，卻漏掉其所屬組織、人脈、原生身分與較早事件；
- 把二手 wiki 彙整當成完整官方結論；
- 做出正確方向的差分推導，但基線資料本身不完整。

因此新增 CANON_EVIDENCE_AUDIT，並固定放在 CANON_DIVERGENCE_GATE **之前**。差分推導只能建立在已完成來源覆蓋檢查的基線上。

### 正史資料不得以「查到一頁」視為完整（CANON_EVIDENCE_AUDIT）

只要使用者要求「完整查」「全部核對」「照原著判斷現在應該怎樣」，或某一正史元素會影響後續長線，就不能以一個 wiki 條目／單一摘要頁當作完整考據。

每個重要主張都要標明證據層級：

- **OFFICIAL_TEXT**：遊戲正文／Key Page／官方對話／官方外傳正文。
- **OFFICIAL_META**：官方 Art Book、Developer Note、官方 Q&A／直播文字等。
- **OFFICIAL_MEDIA**：ProjectMoonOfficial 影音／官方發布內容。
- **RELIABLE_INDEX**：能逐條追到上述一手來源的可靠整理頁。
- **SECONDARY_SUMMARY**：二手整理，只能導航，不可單獨承擔高影響結論。
- **INFERENCE**：由正史＋本線差分推導出的本線結論。
- **UNKNOWN**：目前沒有足夠資料。

### 群體／組織完整核對

若要查一個組織或群體，至少做：
1. 組織總頁／總敘述；
2. 已知每名成員的個別頁／正文出場；
3. 相關 Key Page／Art Book／官方外傳；
4. 與其他組織交叉提及的頁面；
5. 明列「已知」「未具名」「資料不足」成員；
6. 不得把 wiki 自己的彙整句當成官方逐字事實，尤其當頁面內部統計與正文互相矛盾時。

### 「完整」宣稱條件

只有當：
- 已列出主要一手來源；
- 已做交叉來源；
- 已標記未知成員／未知關係；
- 已把官方事實與推論分開；
- 已檢查是否有來源內部矛盾；

才可稱「完整核對到目前公開資料範圍」。

否則只能說「目前查到」「已核對主要來源」，不得自稱完整。

## I.5 正史差分推導（CANON_DIVERGENCE_GATE）

改編 Project Moon 或其他既有作品時，不能只核角色，也不能只查「原作事件順序」。凡正文會碰到的**人物、裝備、能力、組織、歷史、地點、技術、制度、情報、社會後果、稱號、所有權與關係**，都要做「原著基線＋本線分歧」推導。

核心公式：

**本線現況 = 原著分歧點以前已成立基線 + 本線新增因果 − 因分歧而失效的原著後續 + 差分自然導出的連鎖後果**

執行時至少：
1. 找原著基線；
2. 找本線分歧點；
3. 切掉依賴已失效前提的原著後續；
4. 保留未被分歧碰掉的原著基線；
5. 加入本線新增因果；
6. 推導「現在到底是什麼狀態」；
7. 再追至少一至三層連鎖後果。

不得只回答「原作怎樣」，而要回答「照現在這條世界線，**現在應該怎樣**」。

對合聲線，分支專屬推導總表放在：
`04_連續性與索引/12_ProjectMoon正史差分推導總表.md`

只要本章會直接用到未完成差分推導的正史元素，必須先有 **CANON_EVIDENCE_AUDIT = PASS**，之後 **CANON_DIVERGENCE_GATE** 才能 PASS；任一未 PASS，PREWRITE_GATE 都不得 PASS。

## J. 每章至少一個核心看點

每一章至少應具有一個清楚可辨認的「章節核心／看點／功能重心」，使讀者在章末能感覺本章有實際價值，而不是只把人物從 A 點搬到 B 點。

這個核心不等於每章都必須出現重大事件、戰鬥、覺醒、死亡、巨大揭露或主線突破。可成立的章節核心包括但不限於：

- 必要且有戲劇性的資訊統整、報告、盤點或界線確認。
- 人物關係發生細微但真實的變化。
- 某角色作出新的選擇、承認、拒絕、習慣或日常行為。
- 前置鋪墊、任務準備、情報取得、設備／制度／社會運作展示。
- 前一事件的後果處理、善後、責任劃分或社會反應。
- 一場普通委託、物流事故、地方衝突、生活事件或工作問題。
- 一個值得記住的情緒轉折、人物瞬間、觀點或世界細節。
- 伏筆被推進一小步，但不必回收。
- 讓世界證明即使主線不前進，人物與都市仍在自行生活與運作。

資訊統整章可以成立，只要統整本身具有必要性、人物反應與新的理解，不是把既有內容改寫成摘要。例：合聲線第六章開頭透過事故報告確認「未知可以留白」、「不能把個人責任提前合併成合聲整體責任」，就是有效章節看點。

反過來，不要為了滿足「每章有看點」而硬塞重大事件。若一章主要功能是前置、過渡、日常或後果處理，也可以成立；但至少應有一個能讓本章與前後章區分開來的具體價值，例如新的理解、人物推進、因果變化、重要細節或完整小場景。

寫完每章後自檢：
- 本章最值得記住的是什麼？
- 若刪掉整章，會失去哪個人物、因果、資訊、情緒或世界運作價值？
- 若答案只是「人物走到下一個地點」，應補足本章真正的核心，而不是硬加大型事件。


## K. 人物聲音、原作事件穿插與臨界後效應

### K1. 角色性格不是口癖表

- 對話必須讓每個角色保有可辨認的個性、節奏、關係感與當下狀態，但不得把性格簡化成固定標籤、固定功能或機械口癖。
- 「會爆粗口」不等於每句都爆粗；「文質彬彬」不等於任何極端情境都維持完整禮貌；「冷靜」「活潑」「毒舌」「寡言」「自嘲」「哲思」「愛開玩笑」等同樣不能每句都硬展示。
- 性格應被理解為穩定傾向，而不是固定輸出模板。同一人面對朋友、陌生人、上司、家人、敵人，或處於工作、疲勞、受傷、羞恥、憤怒、恐懼、危險、失敗、喪親、公開場合與私人場合時，都可能自然改變措辭、語速、句長、禮貌程度與是否願意說話。
- 喜歡開玩笑的人在嚴肅場合也可能沉默、收斂、只低聲說一句，甚至完全笑不出來；同伴死亡、重傷、重大失敗或真正恐懼時，不得為了維持「搞笑役」功能硬安排大聲逗笑全場的台詞。若角色仍會用玩笑應對壓力，也應符合當時關係與情緒重量，例如乾澀、自嘲、私下、短促，而不是機械緩解氣氛。
- 平時有教養、文質彬彬的人在劇痛、暴怒、失控、極端緊迫或面對特定熟人時，也可能省略禮節、說重話、爆粗或只剩最直接的短句；這不自動等於人物崩壞，關鍵在是否由當下情境與既有人格自然推出。
- 沉默、停頓、答非所問、換話題、說一半停下、重複、口誤、語氣失衡、刻意正常、避開視線等，都可以是人物正在真實生活中的說話反應；不要讓每句台詞都像作者為了展示性格精心準備的「代表句」。
- 同一角色也不必每次都對同類事件做出相同反應。經驗、關係進展、傷勢、心境、近期遭遇與成長都可以改變當下表現，但應保留可追溯的人格連續性。
- 罪人、嚮導、司機、合聲成員、敵人、合作方、學生、師長、店主與普通路人都遵守同一原則：先寫成正在當下生活、思考與說話的人，再保留其穩定人格傾向。
- 不要讓某角色只剩「負責爆粗」「負責哲學」「負責吐槽」「負責冷臉」「負責解說」「負責活躍氣氛」「負責理性收尾」等單一功能。

### K2. 原作主線與分支內容可以互相穿插

- 改編／同人線不必把自創主線與原作主線分成互不干擾的兩條軌道。
- 原作正式事件可以在本線繼續發生、被提前、延後、插入、打斷或因已成立的分支因果而產生偏移；前提是先核對原作來源與本線正典。
- 某個原作任務可以在途中自然碰上分支人物、女聲、E.G.O、扭曲、臨界或其他已建立因素；分支事件也可以被原作任務、公司命令、地方事故或角色私人事件打斷。
- 不要因章節標題／主題而讓世界排隊：角色的人生、任務與外部事件可以同時進行並互相干擾。

### K3. 臨界必須由人物與事件自然推到

- 隊友、主角群、敵人、合作方或其他重要人物，只要其人生與當前事件真正把他推至相應心理／自我臨界，都可以自然進入核心事件；身分不是限制。
- 不得因「輪到某人」「這章需要高潮」「很久沒寫女聲」而硬觸發臨界。
- 既有角色若曾被規劃為未來可能有第二次／延伸式臨界，也只代表可能性；具體發生時間仍由當下因果決定。

### K4. 臨界回歸後必須有餘震，但不強制開會

- 人物從核心／臨界返回後，事件不能像什麼都沒發生一樣立刻平靜帶過；其身體、情緒、注意力、關係或後續行為應留下符合事件重量的餘震。
- 餘震不等於全員立刻圍著當事人長篇討論。若戰鬥、撤離、救援或其他危險仍持續，優先處理安全、補位、確認能否行動、保護當事人或完成眼前任務。
- 安全後的反應可分散在之後數分鐘、數小時甚至數章：沉默、遞水、避免追問、遲來的一句話、失眠、動作變化、主動找特定人物、刻意維持日常、情緒失控、研究需求、警戒或私人關係改變都可以。
- 反應強度與方式依人物個性、彼此關係、是否親身見過女聲、對女聲的感情、是否需要確保安全、是否屬合聲等因素決定。
- 合聲成員或對女聲有深厚正面感情者，得知另一人真正見過她時，可以有更明顯的興奮、安心、親近、好奇、保護欲、沉默或情緒重量；仍不得統一成同一反應，也不得自動跨越對方私人核心界線。
- 沒見過女聲的人也可能好奇、懷疑、擔心、研究、害怕、不知如何安慰、故意不問或把注意力放在作戰安全；這些都應依人物成立。
- 敵人不必尊重臨界。若仍在交戰，對方完全可能利用當事人剛回神的空隙。


## L. 設定外部化的詳細度原則

- GitHub 設定／連續性文件的首要用途是讓後續模型能在換對話後恢復精準執行，不以「檔案越短越好」為目標。
- 對真正會影響執行的內容，優先保存完整條件、例外、資訊順序、角色知識邊界、正反例、後修與禁用版本；若省略後會迫使後續模型自行猜測，寧可保留較長的詳細版本。
- 對話整理進 GitHub 前必須讀到該串後續修正：早期方案若後來被拒絕、覆蓋、降為候選或改名，不得因先出現就當成現行設定。
- 可以同時保存「穩定規則」與「詳細補錄」：穩定設定負責快速定位，詳細補錄負責保留推理邊界與例子；兩者衝突時仍依最新有效正文與後修優先序處理。
- 這項原則只影響設定記錄的完整度，**不要求正文變成條列、說明書或設定集語氣**；小說正文仍依各專案既有敘事風格自然呈現。

## M. 設定討論後自動交接同步（SETTINGS_HANDOFF_SYNC）

只要一段設定討論已經形成任何會影響後續工作的有效內容，就必須在該段討論告一段落時自動同步 GitHub。使用者不需要另外說「記得存」。

### 觸發條件

以下任一成立即觸發：
- 新增硬設定；
- 修改／覆蓋既有設定；
- 確認某候選規劃；
- 將某方案降級為候選／未定；
- 明確作廢舊版本；
- 修正名稱／譯名／術語；
- 改變角色知情、物件狀態、時間線、能力限制或組織關係；
- 新增會影響後續續寫的寫作規則／工作流程。

### 同步順序

1. 先把詳細內容寫進**正確來源檔**：
   - 穩定設定 → 世界觀／分支設定；
   - 當前狀態 → 狀態快照；
   - 角色知情 → 知識矩陣；
   - 候選規劃 → 後續規劃；
   - 作廢／易復活錯誤 → 修正與禁用；
   - 名稱／別名 → 主題與別名索引；
   - 流程規則 → workflow／核定表。
2. 再更新該世界線的 **00_專案交接.md**：
   - 簡短記錄本輪新增／後修／候選／作廢；
   - 指向詳細來源檔；
   - 更新「未同步對話決策」；
   - 若仍有未決衝突，列入「尚未同步項目／待決項目」。
3. 若名稱有正式更正，同時執行 CANONICAL_NAME_MIGRATION。
4. 若本輪新增新的長期檢索詞，同步更新主題／別名索引。
5. 完成 commit。

### 未同步狀態必須即時變化（DIRTY_STATE_MACHINE）

「未同步對話決策」不是只在 SETTINGS_HANDOFF_SYNC 最後才檢查一次，而是**聊天／GitHub 一產生有效差分時就立刻改變狀態**。

固定狀態機：

1. **CLEAN**
   - 目前沒有任何已形成、但尚未寫入正確 GitHub 來源檔的有效決策。
   - 交接檔顯示：
     `未同步對話決策：無（本輪設定討論已完成 SETTINGS_HANDOFF_SYNC）`
     或等價的「無」。

2. **DIRTY**
   - 只要聊天中形成第一個會影響後續工作的有效決策，而該內容尚未寫進正確來源檔，狀態立刻由 CLEAN → DIRTY。
   - **不得等到整段討論結束才第一次標記。**
   - 應立即把這項決策簡短列入世界線 `00_專案交接.md` 的「未同步對話決策」。
   - 後續又形成新的有效決策時，繼續累加。

3. **SYNCING**
   - SETTINGS_HANDOFF_SYNC 開始後，未同步項目仍維持列出。
   - 「正在同步」不等於已同步，不得先清成「無」。
   - 每完成一項正確來源檔寫入，可從未同步清單移除該項；其餘項目繼續保留。

4. **CLEAN／PASS**
   - 只有當所有有效決策都已：
     - 寫入正確來源檔；
     - 完成必要索引／名稱遷移／衝突記錄；
     - 更新交接摘要；
     - commit 成功；
     才能把「未同步對話決策」清成「無」，並判定 SETTINGS_HANDOFF_SYNC = PASS。

5. **FAILED／DIRTY 保留**
   - 若工具失敗、commit 失敗、資料不足或任何項目尚未落盤，狀態保持 DIRTY。
   - 必須列出仍未同步項目，SETTINGS_HANDOFF_SYNC = FAIL。
   - 不得因「大部分已完成」而寫成無。

### 什麼算「有效決策」

會使 CLEAN → DIRTY 的包括：
- 新硬設定；
- 後修／覆蓋；
- 作廢；
- 候選方案被正式確立為「候選」；
- 名稱／譯名修正；
- 角色知情、物件、時間線、能力、組織關係改變；
- 工作流程本身的修正。

不會使 CLEAN → DIRTY 的包括：
- 純提問；
- 尚未形成結論的腦暴；
- 只是重述 GitHub 已有內容，沒有新增／修改。

**已經寫進 GitHub、但仍屬待決／候選的內容，不叫未同步。**它應放在待決項目／候選規劃，而不是 dirty list。

這個狀態機的目的，是處理「討論到一半突然換對話／斷線／工具失敗」：下一個完全零知識的新對話只要讀交接檔，就能知道上一輪有哪些已形成但尚未完全落盤的內容。

### 「未同步對話決策」欄位固定處理

每次 `SETTINGS_HANDOFF_SYNC` 都必須顯式處理世界線 `00_專案交接.md` 的「未同步對話決策」欄位，不能只更新其他檔案後忘記它。

固定程序：

1. **同步開始時**：檢查本輪聊天中所有已形成有效結論的設定／後修／候選／作廢內容。
2. 任何尚未寫入正確 GitHub 來源檔的內容，暫列在：
   - `未同步對話決策：...`
3. 逐項寫入正確來源檔並完成必要的名稱遷移、索引更新、衝突標記。
4. **同步完成前再次核對**：
   - 若所有有效結論均已落盤 → 改成 `未同步對話決策：無（本輪設定討論已完成 SETTINGS_HANDOFF_SYNC）`
   - 若仍有任何一項因工具失敗、資料缺失或尚未處理而沒有寫入 → 保留具體項目，且 **SETTINGS_HANDOFF_SYNC = FAIL**，不得宣稱已完成同步。
5. 「仍未決定但已經寫入 GitHub 的候選／衝突」**不算未同步**；它應放在「待決項目／候選規劃」中，而不是混進「未同步對話決策」。

這個欄位的唯一用途是回答下一個普通對話：

> **上一個對話有沒有任何已形成的有效決策，還只存在聊天裡、尚未進 GitHub？**

### 00_專案交接的角色

- 交接檔**必須每次設定討論後保持最新**，因為下一個普通對話可能立刻接手。
- 交接檔只保存「下一個對話需要立刻知道的差分與指路」，詳細內容仍放來源檔。
- 不要讓交接檔膨脹成第二份設定大全；舊的「最近設定討論差分」可在後續被更新／折疊，只要詳細內容已安全寫入來源檔。
- 若設定討論最後沒有形成任何有效新增／修改，則不需要製造虛假的 GitHub 變更。

完成後可在內部判定：

**SETTINGS_HANDOFF_SYNC = PASS**
