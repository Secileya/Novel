# 小說專案總交接入口

> 本檔是小說 repo 的總接手入口。任何新對話、新模型或隔很久後重新接手小說工作時，先讀本檔，再依指示進入目標專案／世界線。

## 1. 核心原則

GitHub 是小說專案的長期權威記憶。聊天記憶、模型 Memory、摘要與臨時筆記只作導航，不得取代正文與正式設定。

權威優先順序：

1. 最新有效正文
2. 後來明確修正／作廢／撤回聲明
3. 穩定設定檔
4. 連續性、狀態、索引、台帳等工作記憶
5. 聊天記憶與模型 Memory

若衝突，依此順序處理；工作記憶若與正文衝突，先以正文為準，再修正工作記憶。

## 1.1 正式續寫硬閘門

任何專案只要收到「繼續一章／下一章／續寫／接著寫／寫第X章」等正式續寫要求，**不得直接開始正文**。

必須先依 `NOVEL_WORKFLOW_PROTOCOL.md` 與目標世界線專屬核定表完成 PREWRITE_GATE。未 PASS 時，只能做資料核對、缺口處理或草稿評估。

使用者無須每次提醒這條流程；續寫要求本身即視為自動觸發。

## 1.2 舊對話恢復／漏存稽核

若使用者明確提到「之前討論過」「舊對話」「應該有存 GitHub」「GitHub／流程漏掉先前討論」，不得直接假設現有 GitHub 已完整。

先依 `NOVEL_WORKFLOW_PROTOCOL.md` 執行 **CONVERSATION_RECOVERY_GATE**：
- 恢復指定舊對話；
- 讀到後續修正；
- 對照 GitHub；
- 補漏／標記失效版本；
- 若與正式正文衝突，不得靜默改正文。

只有恢復稽核完成後，才進 PREWRITE_GATE。

## 1.3 零知識接手契約（ZERO_CONTEXT_BOOTSTRAP）

任何新對話、新模型、重新載入後的模型，都必須假設自己對專案**完全無知**：

- 不知道 repo 結構；
- 不知道哪個世界線是目前目標；
- 不知道最新正文；
- 不知道設定檔放在哪；
- 不知道哪些舊版本已作廢；
- 不知道哪些名稱曾改過；
- 不知道使用者與前一個模型剛談過什麼；
- 不得因模型本身「好像記得」而跳步。

接手目標不是「大概知道故事」，而是讓一個完全零上下文的新對話，透過 GitHub 文件與固定流程，恢復到**足以做出與前一個已完整接手模型相同層級的判斷**。

### 零知識啟動順序

1. 先讀本檔，確認 repo 的權威規則與目標世界線入口。
2. 再讀 `NOVEL_WORKFLOW_PROTOCOL.md`，取得所有 Gate 與同步規則。
3. 進入目標世界線的 `00_專案交接.md`。
4. 依該交接檔列出的**精確路徑**讀穩定設定、狀態、知識矩陣、修正、台帳、章節索引、主題索引、候選規劃與專屬核定表。
5. 若為改編／同人線，讀該線正史差分／官方核對檔。
6. 再讀最近 2–5 章正文。
7. 以本次任務建立 TOPIC_SWEEP；長檔必須定向抓取實際命中段落。
8. 若使用者提到「以前談過／應該存過」，額外跑 CONVERSATION_RECOVERY_GATE。
9. 若涉及 Project Moon／其他原作元素，先跑 CANON_EVIDENCE_AUDIT，再跑 CANON_DIVERGENCE_GATE；若要正式續寫，最後再跑 PREWRITE_GATE。
10. 任務結束後按 SETTINGS_HANDOFF_SYNC／POSTWRITE 同步。

### 禁止的接手捷徑

- 不能只讀聊天摘要。
- 不能只讀 `00_專案交接.md` 就認為設定已完全恢復。
- 不能因知道某個檔案大概在哪裡就跳過總入口／workflow。
- 不能因 fetch 過長檔就假設相關段落已進上下文。
- 不能把「上一個模型知道」當成「這個模型也知道」。
- 不能靠模型記憶補 Project Moon 正史差分。

### 未同步決策是即時 dirty flag

任何世界線交接檔中的「未同步對話決策」都要當成**即時狀態**，不是事後備註：
- 出現有效新決策、尚未進正確來源檔 → 立刻 DIRTY；
- 同步進行中 → 保留未同步項目；
- 全部來源檔＋索引＋交接＋commit 成功 → 才能 CLEAN；
- 新對話若讀到非空未同步項目，應先恢復／完成同步，不得直接假設 GitHub 已完整。

### 接手完成自證

在開始重大設定判斷或正式續寫前，模型至少要能從文件中回答：

- 目前是哪條世界線？
- 最新有效正文是哪一章、停在哪個場景？
- 當前人物／物件／傷勢／知識邊界是什麼？
- 哪些設定是硬設定、哪些只是候選？
- 最近有哪些後修、改名、作廢或待決衝突？
- 本次任務涉及哪些主題，已在哪些文件中實際命中？
- 若涉及原作，目前本線相對原作有哪些已成立分歧？

答不出其中任一項，就仍視為未完成接手。

## 4. 世界線隔離

## 4.1 上位世界設定繼承，不等於兄弟分支互相污染

「分支隔離」只禁止把**其他分支專屬已發生事件／角色知情／關係進度／物件狀態**直接搬過來；它**不代表分支脫離上位共同世界**。

固定繼承層級：

1. 上位作品／世界總設定
2. 該世界線共同歷史與制度
3. 目前分支追加／覆蓋
4. 目前分支正式正文

因此只要上位總檔中的內容屬於：
- 世界制度；
- 都市生態；
- 組織、協會、翼、五指、事務所、工坊；
- 地區、後巷、巢、交通、產業；
- 清道夫、辛迪加、異想體等世界既存存在；
- 都市危險分類與委託制度；
- 已成立的共同歷史；
- 尚未被本分支明確否定的世界級任務／長期因果；

就應視為本分支共同底層，**除非目前分支有明確衝突／覆蓋**。

兄弟分支的「已發生事件」仍不可互相繼承。



正史、非正史分支與不同作品永久分離。兄弟分支可作寫法／能力表現參考，但其中已發生事件、角色知情、關係進度、取得物件與時間線結果，除非目前世界線正文獨立建立，否則一律視為未發生。

## 5. Checkpoint 原則

「正典 checkpoint」只代表：某一 commit 時，正文與該線工作記憶已完成同步。

分支交接檔應保存：
- checkpoint commit SHA
- 最新正文
- 狀態資料同步到哪一章
- 下一自然入口
- 尚未同步項目

若 GitHub HEAD 晚於 checkpoint，先查看其後 commits，判斷是否只有交接指標／文檔更新，或正文已前進。

## 6. 完成工作後

每完成一章或一批正式正文：
- 寫入正文
- 更新當前狀態
- 更新未完成因果
- 更新角色知識矩陣
- 有永久設定變動時更新設定
- 有作廢內容時更新修正禁用
- 更新章節索引
- 有交易／物件／契約變動時更新台帳
- commit
- 再把已同步 commit SHA 寫入該線交接檔

詳細流程以 `NOVEL_WORKFLOW_PROTOCOL.md` 為準。
