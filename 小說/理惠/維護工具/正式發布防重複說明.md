# 佐伯理惠｜正式發布防重複

**唯一正式第22篇**：[今晚換惠惠牽你](../正文/第五天/22_今晚換惠惠牽你.md)。〈今晚不算分〉[保存在特殊](../特殊/03_第22篇重複發布備選稿_今晚不算分.md)，不是下一個事件。正式索引47件；好感度110／110。所有正典以事件閱讀順序及目前人物狀態為準。

## 發布前

在最新 main 的完整倉庫執行：

```bash
node 小說/理惠/維護工具/測試正式篇章唯一性.mjs
node 小說/理惠/維護工具/檢查正式篇章唯一性.mjs
```

失敗就停止提交。機器檢查「同一故事日／篇號不得有第二篇正文」「編號正文必須進入正式索引」「現行分日鏡像必須唯一且與正文一致」「人物狀態須指向最新一篇」。三個歷史轉址／整合導覽檔可保留，不能包含另一份正文。

## 防重複提交及併發保護

1. **每次重試都重新查遠端** main 的 HEAD、正式索引、最新篇號下所有正文檔、同號分日鏡像和目前人物狀態。以來源當輪識別、承接前篇路徑與末句、預定篇號及定稿正文識別作**冪等鍵**。
2. 若同輪已提交成功，直接回傳原 GitHub commit 和篇章連結，不建立任何新檔。若編號已占用而內容不同，**停止並向作者確認**；不得自動改名或當作下一篇。
3. 新篇寫入前確認正文／鏡像／索引／目前狀態一致，先執行防重複檢查。合法修稿覆寫既有同一篇路徑，不新增事件。
4. GitHub Git Data 發布時用當輪讀到的 main HEAD 作 `update_ref(expected_sha=原HEAD)` 租約；HEAD 變動就重新讀取、重新查冪等鍵，**禁止 force、禁止盲目重送**。GitHub Contents API 的單檔 SHA 不足以防止不同檔名同號競爭。
5. 只有在 commit 存在、遠端正文及鏡像回讀一致、索引和人物游標皆已更新後，才宣稱整輪完整同步；部分成功時只補剩餘檔案，不重新建立正文。

## GitHub 自動驗證

`.github/workflows/理惠正式篇章防重複.yml` 對理惠內容的 push / PR 自動執行上述檢查。**CI 偵測錯誤但不保證阻止未保護 main 上的直接 push**；要在合併前硬性阻擋，需由倉庫管理者設定 branch protection／ruleset 的必須通過檢查，並限制直接推送。腳本只檢查正典唯一性，不用文字相似度猜故事是否真的重複。
