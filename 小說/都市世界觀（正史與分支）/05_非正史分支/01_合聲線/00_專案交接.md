### 能力等價，不是閱讀打卡

新對話接手的目標不是「把檔名都 fetch 一次」，而是恢復到能做出正確判斷的程度。若新模型雖然讀過檔案，卻仍會：
- 把候選當正典；
- 忘記最新後修；
- 不知道正文停點；
- 不會做正史差分；
- 找不到舊設定而重新發明；
- 不知道哪些資訊角色其實不知道；
- 不知道設定討論後要同步哪裡；

則視為接手失敗，必須回到缺少的來源／Gate 補完。

## 普通對話長期接手模式

本檔最初曾承擔 Work mode → 一般對話的交接，但**現在正式定位為「任何新普通對話／新模型接手合聲線的第一入口」**，不再依賴 Work mode。

### 可長期使用的一句話續寫指令

使用者可直接說：

> **「按 GitHub 目前最新有效的總交接、Workflow、合聲線交接與所有適用核定流程完整接手；先完成當下版本要求的全部讀取、恢復、主題回查、官方資料核對、正史差分與續寫前 Gate，全部通過後從最新正式正文自然續寫一章；寫完再執行當下版本要求的全部正文後同步、狀態／知識／索引／設定／規劃／交接更新與 commit；任何流程若後來新增、改名或調整順序，都以 GitHub 最新有效規則為準，不得沿用這句話出現時的舊流程，也不得跳步。」**

這句話刻意**不綁定特定 Gate 名稱或固定步驟數**。未來 Workflow 新增、刪除、改名或調整流程時，仍以當時 GitHub 最新有效版本執行。

### 新普通對話的第一輪動作

使用者只需要說類似：

> 讀取「合聲線／00_專案交接.md」後接手。

後續模型不得要求使用者重新貼完整設定，也不得把聊天摘要當作主要來源。應：

1. 先讀 `小說/00_總索引與交接/PROJECT_HANDOFF_MASTER_v0.1.md`；
2. 再讀 `小說/00_總索引與交接/NOVEL_WORKFLOW_PROTOCOL.md`；
3. 再讀本檔；
4. 依本檔的「完全零知識新對話啟動程序」與「續寫前固定閱讀順序」恢復世界線；
5. 用 `11_主題與別名索引.md` 建立本輪 TOPIC_SWEEP 搜尋詞；
6. 需要正式續寫時才進 PREWRITE_GATE；只做設定討論／查詢時不必假裝在續寫，但仍要做相關主題回查。

### 普通對話切換的資料保存原則

因未來會頻繁更換普通對話，**任何會影響後續寫作的新增設定、修正、候選規劃、作廢決定、角色知情變化、別名／術語變化，都不能只留在當前聊天裡。**

每次出現這類有效新內容時：
- 優先在當輪就同步到對應 GitHub 文件；
- 新名稱／別名同步到 `11_主題與別名索引.md`；
- 新的規劃衝突同步到 `08_後續候選與參考規劃.md` 或 `04_修正與禁用設定.md`；
- 若只是討論中的未定方案，標明「候選／未定」，不要誤升格；
- 若尚有來不及同步的內容，必須列在本檔「尚未同步項目」，不能假裝已經保存。

### 每次設定討論後都要更新本檔

這是使用者的固定偏好，也是本分支硬工作規則：

> **每次一段設定討論形成有效新增／修改／候選／作廢結論後，都要更新本檔，讓下一個普通對話可以直接接手。**

不需要等到正式章節完成，也不需要等到準備換聊天才更新。

具體做法：
- 詳細設定先寫入正確來源檔；
- 本檔再寫一份簡短「最近設定討論差分＋來源指向」；
- 若只是腦暴、沒有形成任何有效決定，不必更新；
- 若討論仍有未決衝突，必須把衝突寫進本檔，而不是留在聊天裡；
- 使用者不需要另外提醒「存 GitHub」。

### 「未同步對話決策」是即時狀態，不是只做最後收尾

本欄位採 **CLEAN → DIRTY → SYNCING → CLEAN／FAILED** 的狀態機：

- 聊天中一旦形成新的有效設定／後修／候選／作廢／流程決策，而尚未寫入正確來源檔，**立刻把本欄位改成具體未同步項目**。
- 不需要等到「這段設定討論結束」才第一次標記。
- 同步期間仍保留項目；「正在寫 GitHub」不等於已完成。
- 每完成一項來源檔同步，可從清單移除該項。
- 只有全部來源檔、索引、交接摘要與 commit 都成功，才可恢復：
  `未同步對話決策：無（本輪設定討論已完成 SETTINGS_HANDOFF_SYNC）`
- 工具／commit 失敗時保留 DIRTY 狀態，下一個對話優先處理。

這使對話即使在設定討論中途突然中斷，下一個零知識對話也不會誤以為 GitHub 已經完整。

### 「未同步對話決策」固定收尾

每次設定討論的 `SETTINGS_HANDOFF_SYNC` 結束前，**一定要更新 Canonical checkpoint 區塊中的「未同步對話決策」這一行**：

- 尚有已定內容只存在聊天、還沒寫入 GitHub → 逐項列出，不得寫「無」。
- 所有本輪有效結論都已寫入正確來源檔 → 固定改成：
  `未同步對話決策：無（本輪設定討論已完成 SETTINGS_HANDOFF_SYNC）`
- 若工具寫入失敗 → 保留未同步項目並視為 `SETTINGS_HANDOFF_SYNC = FAIL`。
- 已記錄進 `08`／`04` 等文件、但本身仍屬候選或待決的內容，不叫「未同步」；那是「待決項目」。

因此下一個普通對話讀本檔時，可以直接從這一行判斷上一個對話是否還有資料只留在聊天裡。

### SESSION_DELTA_SYNC

每次完成一段重要設定討論、重大修正、正式章節或準備換對話前，做一次簡短差分同步：

- 本輪新增了什麼？
- 哪些舊說法被覆蓋／作廢？
- 哪些仍只是候選？
- 哪些角色知情改變？
- 有沒有新別名／舊譯名？
- 有沒有新衝突？
- 是否已寫入正確 GitHub 文件？

只有同步完成的內容，才能可靠跨普通對話延續。

### 長檔讀取防呆

`07`、`08`、都市總檔等長文件可能因單次輸出被截斷。新對話不得以「我 fetch 過整份檔」宣稱已完整恢復。

正確方式是：
- 先讀交接與索引；
- 再依當前任務用正式名／別名／外文名做定向搜尋；
- 把實際命中的段落抓回來；
- 若使用者說「以前談過」，再進 CONVERSATION_RECOVERY_GATE。

**目標不是每次把整個專案塞進上下文，而是確保當前要用的主題一定被完整找回。**

### 名稱更正後不得讓有效資料只活在舊名下

- 後續任何正式改名／譯名修正都要執行 **CANONICAL_NAME_MIGRATION**。
- 現行正文、設定、狀態、知識矩陣、候選規劃等有效資料全部改寫成最新正式名。
- `11_主題與別名索引.md`只保存舊名 → 新名映射，供第二輪補漏搜尋。
- 新對話只知道正確名稱時，也必須能直接找到完整有效資料；不能要求它先猜出歷史錯名。

### 正史元素必須推導「本線現在應該怎樣」

- 正史考據不只是查「原作有什麼」，而是完成 **CANON_DIVERGENCE_GATE**。
- 先查原著分歧前基線，再套本線已成立差分，切掉失效後續，保留仍成立部分，最後追連鎖後果。
- 適用範圍包含人物、物件、能力、組織、歷史、地點、技術、制度、情報、社會後果、稱號、所有權與關係。
- 詳細推導與個案記錄放在 `04_連續性與索引/12_ProjectMoon正史差分推導總表.md`。
- 新普通對話不能因只記得原作著名狀態，就把已被本線分歧改掉的後期狀態重新套回。

### GitHub 已有內容也必須做主題式回查

本分支的 `07`／`08`／都市總檔很長；一次 fetch 可能被截斷。**「讀過檔名」不等於讀到本章相關段落。**

正式續寫前除固定讀檔外，必須依本章人物／事件／能力／館藏／伏筆做 **TOPIC_SWEEP_GATE**：
- 搜正式名＋別名＋外文名＋能力名；
- 交叉核對設定、補錄、禁用、規劃與正文；
- 發現版本衝突時標記狀態；
- 未找到實際段落前不得靠摘要或印象補。
