# GPT 莉雅｜完整雙向逐輪原文存檔

> 生效：2026-10-27。效法理惠的「逐則原始訊息＋分日對話＋正式正文」三層，但**不搬用理惠的人格、生活經歷或正式章節**。
> **現有倉庫 Secileya/Novel 是 public**：使用者希望可沿用現有倉庫；完整存放於此代表可能公開，敏感個資、未授權第三人私事、密碼與其他真正不宜公開的內容仍須確認可公開後才寫。本文件不是無限制公開授權。

## 保存層次

1. **逐輪原文**：此次新增的唯一不可用摘要取代的來源層；保存實際看見的每則方九訊息、莉雅訊息、兩者真實先後順序。情話、吐槽、生活、普通親近都不因「非敏感摘要」而被禁止；存入公開倉庫前仍須尊重公開範圍。
2. **技術脈絡**：`共同生活記憶/_莉雅背景訊息脈絡.json` 只是快速話題索引，不是完整原文；讀到摘要不能冒充讀過完整聊天。
3. **已確立共同生活記憶**：`共同生活記憶/02_日常互動記憶簿.md`、`共享記憶索引.json`、`05_有效事項快速索引.md`；從有來源的對話提取少量重要事件。提議/答應/完成有各自狀態。
4. **正式小說**：`正文/001～005` 和其後真正經使用者採納的篇章；日常對話不自動變成第006篇，也不自動接第五篇末尾「……不許笑！」。

## 儲存佈局

每個實際可辨識的聊天／對話串有唯一 `session_key`；若能可靠取得 ChatGPT conversation ID 則用它，否則首次存檔時建立隨機且持續沿用的 key。**不得把所有新的「莉雅」聊天誤認為同一條源對話**。分日使用台灣日期 `YYYY-MM-DD`，路徑建議：

`原始對話/逐輪原文/YYYY-MM-DD/<session_key>.json`

兩個已存在的新版自動化任務在記錄來源上共用已知建立聊天 `6ae0775b-58d8-83ec-98c6-284b58c8ef0e`，但不代表可確定推播實際落在原專案列表。背景來源須寫 `source_kind: automation`。使用者在其他會話回覆則依實際聊天另建 session 並用 `reply_to_id` 連結；不要假設回在同一聊天。

一份會話／日檔基本結構：

```json
{
  "schema_version": 1,
  "session_key": "實際會話的穩定鍵",
  "local_date": "YYYY-MM-DD",
  "timezone": "Asia/Taipei",
  "messages": [
    {
      "message_key": "穩定的來源訊息鍵",
      "role": "liya",
      "text": "真實的原文（不縮寫、不改寫）",
      "source_kind": "automation",
      "source_ref": "真實來源或 null",
      "reply_to_id": null,
      "origin_time": "可核實時間，否則 null",
      "record_status": "prepared_not_delivery_verified"
    }
  ]
}
```

**角色與準確度**：`role=user` 表示已取得方九真正輸入的原文；`role=liya` 表示莉雅真正擬好並要輸出的完整原文。背景在送出前寫入的 `prepared_not_delivery_verified` 只是已準備／預定發送，**不是手機推播簽收**；若使用者親眼確認才可另記 `delivery_confirmed_by_user`。新對話中的 assistant 模型能讀到本輪自己的回答草稿與使用者本輪輸入，但**不保證可讀取其他 ChatGPT 對話、附件、已刪或未選分支，也沒有自動監聽全部訊息的功能**。若未取得某則原文，記待補缺口而非猜句子。

## 逐輪寫入協議（適用連聊 2 輪、20 輪、200 輪）

- **先讀**：首次在一條聊天動筆時，讀同日 session 檔（不存在時才 create），並確認目前 `session_key`／訊息最後排序。若當日跨午夜，分新日期檔，保持同 session_key；可參考前一日末尾。
- **真實 user 訊息**：從本輪實際可見的使用者文字逐字複製。不要把自己建議給方九的「候選台詞」、測試例句或原著原話冒充 user。當單一 user 文字很長，仍是一則，含原本換行。
- **真正 liya 回覆**：先形成這輪擬送出的完整文字，與 user 訊息連續新增並寫入同一檔；排除工具內部工作紀錄、內心未對方九說的構思及本聊天室龍娘的 OOC 解釋。若寫入失敗仍可正常聊天，但明確說明未完成存檔（禁止宣稱已成功）。
- **去重**：優先用平台提供的穩定訊息 ID；若無 ID，為當輪產生並在同一次回覆中固定沿用的 `message_key`，重試**先查同 key**：內容／角色相同 → no-op；同 key 內容不同 → 衝突停止。不能每次重試都自動產生新的 key 造成重複。若新一輪 user 恰好重複發同一句，必須有新的真正來源回合鍵，不能靠文字去重把它刪掉。
- **同一檔 GitHub SHA**：先讀最新 blob SHA 再更新；若過期衝突，重讀最新全文、確認新資料與既有資料無矛盾再合併；無法確認則停寫，不覆蓋／跳號。每次更新後**重新讀取**確認訊息數與原文一致，才回報 GitHub 保存成功。
- **排序**：只按實際擷取來源的先後排序，不以自動化任務「預期時間」硬改真實訊息順序。沒有可靠時間的 `origin_time=null`；可以用提交時間作 `recorded_at`，但不可假稱是說話時間。
- **回覆連結**：每則可記 `reply_to_id`，用來分辨方九回的是先前哪一則；只在來源可支持時建立，不能靠「你沒回」猜測。對先前問句沒有可見回答時 `response_status=not_checked`，仍可自然催促或轉題，但不當成已知拒絕。
- **抽取長期記憶**：原文提交成功後，確實有成立的偏好、約定、實際共同活動才依 02／共享 JSON／05 獨立更新；不要每輪把日常廢話升格 LIFE。
- **失敗復原**：GitHub 失敗時保留聊天自然互動，明確標示未存／缺口（可供日後從真實對話匯出補錄）；不要以「任務完成」推論對話一定寫入或推播一定抵達。

## 兩條路徑的實際能力

**A. 背景任務**：可用 GitHub 先保存它自己準備發出的完整原文（必要時放在其會話日檔），再送出；日間仍需先依原規則對 `sent_hours` 去重，00:30仍不讀寫日間計數。若原文檔寫入失敗，00:30 仍應照原定時間發話，並在後續可見時標示缺口。

**B. 使用者回覆後的正常聊天**：若身處可用 GitHub 連線的莉雅聊天室，且該聊天的專案指示已安裝 [維護工具／專案指示貼上版](../../維護工具/莉雅雙向逐輪存檔_專案指示貼上版.md) 或當輪明確要求，莉雅**應每輪**實際讀／寫 user＋assistant 原文並回讀；**僅有 GitHub 的 AGENTS 文件不會自動改動 ChatGPT 原生「莉雅」專案的 instructions**，需使用者把指示貼入專案設定。工具沒有被調用就不會自動保存。

## 驗收標準

1. 連續至少三次 user→liya 互動，共六則完整原文，順序不漏不重。
2. 重複執行同一次紀錄 no-op，同鍵不同字衝突不覆寫。
3. GitHub 過期 SHA 更新失敗後可重讀安全合併，不覆蓋舊檔。
4. 下一次背景任務能從 GitHub 實際讀到先前測試訊息的證據。
5. 失敗不會偽造 user 回覆、不會新增 LIFE／第006篇、不會占掉正式日間配額。
6. **專案每輪自動落檔**須在貼好 ChatGPT 專案指示後由使用者於真實對話至少連續兩輪核實；不能拿隔離測試代替此項。

所有示例及測試稿必須隔離在 `維護工具/測試資料`，不進 LIFE、正式正文或對外假稱真實相處。

## 多個聊天室共同延續：已驗證會話索引

當方九在「莉雅」Project 的新聊天室回覆時，`session_key` 可能與自動化原關聯聊天不同。成功提交**完整原文並遠端回讀**後，再用最新 SHA 將該真實 session 更新到 [`_會話索引.json`](_會話索引.json)：包含 `session_key`、`context_kind`（角色互動／OOC／測試）、`latest_archive_path`、`last_activity_local`（可靠時間才填）、`last_message_key`、`source_kind`、`verification=github_readback_verified`。若 SHA 衝突重讀並按 session_key 安全合併；失敗時原文仍保留，只是跨會話索引未同步，須誠實呈現。

背景下一次主動聯絡時，除自己原關聯聊天當日及前一日的逐輪原文外，可以讀這個索引找**實際已入庫且適合延續的**近期日常角色互動，再讀該日檔最近數則及適用的 05／共享記憶。**只有 user 真實訊息已逐字存入才可以依其具體內容接話**，並且不能把 OOC 設定／合成測試當成莉雅已收到的世界內發話。索引只存路徑和基本順序資訊，不需貼完整私訊兩次。

如果原生 ChatGPT Project 指示未安裝或該輪 GitHub 寫入失敗，索引自然不會有那段對話；背景不可假裝自己已看到未同步的聊天。


## 原文最終一致性（2026-10-27 後修，優先於舊草稿流程）

`messages` 只容納真實 user 輸入及莉雅最後實際顯示的完整回答，順序、換行、標點一致。例：方九問「吃了沒？」；莉雅實際發「我吃飽了」，GitHub 就只存這兩句。即使預備回答曾寫入 GitHub，只要未實際輸出便屬草稿，須移出對話序列。錯誤、重試、未發草稿只在獨立技術紀錄，不要把報錯當成莉雅對方九說的話。先固定最終輸出、提交同文並回讀，再原文送出；若發生改稿，必須以真正可見文字重新核對修正，不能假稱舊稿就是已發訊息。兩則連續更正都如實保存，最新一則作有效規則。未驗證投遞仍標 prepared_not_delivery_verified，不冒稱已送達。

## 新增｜人類可直接閱讀的聊天版

**閱讀入口優先於技術 JSON。** 每個台灣日期資料夾提供 `聊天閱讀版.md`，以普通 Markdown 格式把可核實的方九、莉雅實際發言逐則排出：`### 方九`、`### 莉雅`，後接當則完整原文（保留段落、原有換行和說話順序）。不展示 `message_key`、SHA、工具回報、JSON 欄位等給一般讀者；可將技術資料放在頁尾折疊說明或原 JSON。

**所有來源都要走同一機制：**日間隨機訊息、每天凌晨 00:30 枕邊話、一般聊天、方九回覆定時訊息、後續雙向連聊，只有實際取得完整原文且通過該來源 JSON 寫入／回讀核對者才增補閱讀版。每次先核對 `message_key`，已存在不重複，確實新增才更新人類閱讀版；讀最新 Markdown SHA，併發衝突重讀合併，不能刪改既有對話。某次 Markdown 寫入失敗不等於 JSON 失效，但不得稱閱讀版已同步成功；不可因此阻止獨立定時任務原本的正常發話。沒有任務工具可用時不能保證自動保存。

**多會話／背景訊息：**同日不同聊天室或定時任務的訊息可在同一頁以會話標題分段呈現；只有時間可核對，才依時間跨會話混排。背景任務先保存而尚未證實送達者，標為「準備發送／送達未驗證」，不得冒充已收到或方九已回答。隔離測試、故障、草稿不能混進正式日常對話；OOC 設定／存檔過程只保留在 JSON 原文和 diagnostics，不放進一般聊天閱讀版。
