# 巨構世界｜來源新增、既有檔案更新與歷史批次 CI 處理（2026-11-11）

> **工作流程／非Canon**。本文件不新增或批准小說設定，不修改原始來源，也不把編輯性驗收視為作者採案。正式正文仍 0 章／PREWRITE HOLD。以每次最新 Git `main` 與當次 Actions 實際結果為準。

## 一、什麼是「366份通過CI」？

- 2026-11-11 驗證：Git `main` 的來源掃描有 **366份**（排除設定關聯引擎、AGENTS/GEMINI 指示檔），原文種類 349 MD、6 JSON、8 SVG、3 TXT。
- 主 CI（提交 `04e4004d21777e3ef1e8c0a33b6a10689ed2dc4f`）：https://github.com/Secileya/Novel/actions/runs/42989497889 ，日誌 `Shard overlay valid: 31 shards, 366 editorial file records, 7162 mapped claims`、`全庫來源整檔驗收：366/366份…0份尚待驗收`。
- Drive 索引 CI：https://github.com/Secileya/Novel/actions/runs/42989497965 ，**不是**代替整檔語義驗收的檢查。
- 從本 SOP 提交後，主 CI 另以 `mega-all-source-receipts` artifact 公開當次 **逐檔** `source_path`、`source_sha`、`review_status`、`invalidation_reasons`、全域 `faults`；artifact 存活期間受 GitHub retention-days=90 限制。CI 驗證的是內容版本、行號、引文、後修 SHA、索引完整性與簽核程序；**不保證原稿內容語義無誤，更不是Canon批准**。
- GitHub Actions 的舊成功 run 只證明**當時提交樹**，不自動證明未來 HEAD。Drive auto-index 可產生只有索引檔變化的新 HEAD；須以 `git diff`／逐檔 SHA 確認來源是否真的改動，不因 HEAD 變化就一律宣稱來源失效。

## 二、歷史第一批～第五十二批的檔案被更新

1. **發現**：每次 push／PR 跑 `全量來源_動態納管與驗收.mjs`，按當前提交樹列出全體檔案並與驗收憑證的 Git **blob SHA** 比對。改動到一個位元即可導致 SHA 不同；已簽核檔標成 `REVOKED_RECHECK_REQUIRED`。舊 CI 歷史紀錄不刪也不改寫，不能讓舊 SHA 的合格狀態冒充新檔合格。
2. **影響**：執行 `批量審核_語義缺口與跨批影響.mjs --impact "<變動檔案相對路徑>"` 取得已登記的跨批直接／遞迴依賴。再查角色知情、道具物權、地理、容器、版本取代及其他未完整登記的語義關聯。**影響圖只覆蓋已登記依賴，不能說所有下游都已自動找全**。
3. **複核**：對新版原文比對舊版、重新判斷新增／刪除／修改的實質意思、作者後修權威、引文行號與人物時序；逐檔出新版本 SHA 與有效證據。不需重讀所有其他無關的歷史批次，但凡依賴 SHA／語義被波及者均需重驗。
4. **回寫（避免重複計數）**：原驗收歷史保留；使用 Manifest 內 append-only `revalidations` 與 `來源後修_證據覆核.mjs` 的同路徑替換證明，**不是**把已驗收檔重塞入一個新 `staged_attestations` 批次（會觸發 `ALREADY_ACCEPTED`）。目前已有3個 SHA 覆核分片、18份來源重驗經反向測試通過；既有精確插入／行號搬移的覆核機制已實證。**對任意大幅改寫、非插入式位移或圖關係變更，現有覆核器不能保證自動重映射全部舊引文；先人工盤點、增強覆核器和測試再宣告新版通過**。
5. **重驗**：跑全庫整檔／跨批／反向測試與主 CI，驗證新的 SHA、全文覆蓋、權威後修、所有受影響依賴。成功後才恢復 `FULL_FILE_EDITORIAL_VERIFIED`。新版與舊版證據可並存，但「目前有效」只計同一路徑一份。

## 三、未來新增、移動、更名、刪除

| Git 變更 | 當下狀態 | 需要的動作 |
|---|---|---|
| 新增第367份文字來源 | `NEW_SOURCE_AUTO_QUEUED` | 全文語義讀取、來源與版本分類、逐行錨點、候選／Canon邊界、非Canon雙向關聯、專用分片／Manifest、工作板＋經驗日誌＋交接同步；未做完不能報367／367 |

| 已驗收檔改寫 | `REVOKED_RECHECK_REQUIRED` | 比對SHA、證據與權威，盤點跨批依賴，產生不重計的覆核替換後重新跑CI |
| 搬移／更名 | 舊路徑失蹤＋新路徑出現 | 建搬移對照、核內容 SHA、修正來源路徑及所有引用；**不能**只當單純新檔，避免同一資料被計兩份 |

**例**：366份全部有效 → 第一批某A檔SHA改動 → 原證書失效；沒有其他受影響來源時為 `365/366`，若依賴也失效則更多待審。新增B檔而尚未審核則為 `366/367`；若同時A又失效則是 `365/367`。這些是示例，不是現況。

## 四、未來每輪固定檢查

1. 讀當前 HEAD，枚舉來源實際路徑與 blob SHA，確認 Git tree 沒截斷。
2. 檢查最新主 CI（不是只看歷史 batch URL）、逐檔驗收 artifact、來源新增／更新／遺失與後修依賴；先回報 `目前有效/目前來源` 與 `需重驗`。
3. 有變動先做失效與影響清單，無變動改做高風險語義抽查（候選版本優先權、貨幣、道具、角色知情與時間地理）。避免虛構新驗收批數。
4. 原文不覆蓋、Canon 不擅升；每次完成回寫完整經驗／工作板／交接並核主CI。CI失敗時不能稱為已通過。
