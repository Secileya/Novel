# 《巨構世界（法月懷造物）》｜GitHub 資料保存、PR 與合併的作者指定工作規則

> **狀態：作者明確確認的工作流程規則（2026-11-05）**。這是**存檔／交接／版控規範，不是小說世界 Canon**。適用於後續 ChatGPT 對話、接手本 GitHub 專案的其他 AI 工作階段；若使用者之後明確修改，以較新的要求為準。

## 0. 給新接手對話的最優先提醒

- **不要只在聊天裡口頭答應**。使用者要求新增或更新的可留存研究、原稿、修稿、QA、整理結果，應按此規則**實際寫入 `Secileya/Novel` 的 `main` 並重新讀取驗證**。
- **預設直接提交 `main`，不是預設開分支／PR。** 不要為了「保護 Canon」「候選未定案」而把**新建檔案**無理由留在開放 PR；候選內容可存在 `main`，標明 `CANDIDATE / NON-CANON`，並與正式正文、已批准設定分離。
- **PR 不等於已合併、分支已存不等於 `main` 已存**。不能把「開 PR」模糊稱作已存入主分支。使用者不應為了把正常任務完成而再下第二道「合併 PR」指令。
- 不要把「Gemini 在回答末尾習慣詢問要不要寫下一章」當成使用者要求切換章節；確認目前是在修訂哪章、原文的真正章末。對「整理問題交給其他 AI 修」不得越界改寫正文。

## 1. 預設流程（非破壞性工作）

對新增研究紀錄、分析報告、待定章稿、來源轉存、比較、修訂候選、QA、交接及索引：
1. 先讀 `main` 最新 HEAD、現有檔名與權威資料，核對是否已存在／是否需要建立新版本。
2. 保留既有來源與候選，不默默覆寫；新稿使用明確且不衝突的版號與檔名，作品狀態仍按作者實際批准。
3. **直接建立或更新 `main`**（若該操作的權限和安全性允許），無需預設新 PR。對內容可歧義或需要特別隔離的稿件明標 `NON-CANON`。
4. 使用 GitHub 讀回 `main` 的檔案，驗證內容確實存在且版本／路徑正確；必要時核對 HEAD。
5. 回覆提供可點開的 `main` 檔案連結、變更內容、是否更動正式正史、commit 或實際儲存狀態；**只在真的確認合併後才說「已合併」**。
6. 若寫入失敗、權限不允許、連線錯誤，應如實說明，不能宣稱已儲存或已合併。

## 2. 什麼情況才考慮分支／PR

- 需要**大規模重新命名、搬移、刪除、覆寫**歷史正文或來源文件；
- 可能破壞既有可讀鏈、索引、穩定設定、權威 Canon 或同時牽動大量檔案；
- 大量自動轉換、需要核查差異，或 GitHub 分支衝突；
- 使用者**明確指定**要求先 PR 審核。

如果確實開 PR，需**當次說明**：為何不能直接提交 `main`、PR 編號／網址、哪些檔案只在分支、是否已合併、還缺什麼。對本可安全合併且符合作者任務的保存作業，應在核對後主動完成合併並驗證；**不可任意把 Draft PR 留著，等使用者追問才合併**。若需要額外授權、存在未解衝突或會造成破壞，則停下並如實交代，不能為了「一定合併」越過風險。

## 3. 權威與候選區分

- **GitHub `main` 是資料保存的預設落點，不是小說正史開關。**
- `CANDIDATE`、`NON-CANON`、`PREWRITE HOLD` 等標示保持有效；保存、合併、PR 關閉都不會讓候選升格為正式章節。
- 作者說「把問題整理給 Gemini 修」，就應交付**可複製的問題清單與來源**，而不是自行更動指定來源的小說正文。
- 明確區分：來源正文、Gemini 的「當前章修訂設計」、下一章邀請句、下一章候選正文；先核對具體章末再決定接續。

## 4. 為何訂立

2026-11-04～05 曾發生 PR #4 建立後延至隔日合併，而後建的 #5 當日先合併；又有 PR #21 先以 Draft 留在分支，使用者追問後才合併。使用者明確指出此流程不一致，造成誤以為所有成果都已進入 `main`。因此正式固定**「預設直接 `main`、例外才 PR、操作後讀回驗證、交付時明報狀態」**，避免再重複。
